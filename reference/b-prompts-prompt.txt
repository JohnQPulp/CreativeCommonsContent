This task will be about the the background half of the first half of the image-generating step: the setting up of the background image prompts to be ready for generation. This involves creating an `images` array, to be used as part of an automated image generation python script (the actual running of which is out-of-scope for this current subtask — don't actually do any image generating yet).

(Note that for this particular example set, a few backgrounds were excluded as being complex edge cases that required multiple manual edit-prompting generations — in particular those to do with the titular changing portrait itself — but in general you should assume that the input+output set of backgrounds represents the full range of backgrounds needed throughout the book, and that each background prompt should be theoretically capable of one-shot output the desired result. Even if, as we'll see later on, image generations usually tend to take multiple re-generations to get right.)



To explain the above:

The `images` array is made up of sub-arrays, each of length 4.

The first item in the subarrays are the names of the various backgrounds, arranged in chronological order based on the first appearances of each background. (Noting that a background can be reused multiple times.)

The second item in the subarrays is the array of reference images to be used for the image generation. By default, this is set to just be `brefs`, an array with a single style reference image for the desired "literary cross-hatching" style, defined like so: `brefs = ["helpers/b-example"]`. Most prompts will only need to use this style reference, though others sometimes need to reference a different generated background for location/setting/physicality consistency. Since the second subarray items are also arrays (sub-subarrays), multiple reference images can be used if needed, though usually this isn't necessary.

The third and fourth subarray items together form the the full text portion of the image generation prompt, putting together a boilerplate first half of the prompt like `bprompt` or `bupdate` with a detailed second half that described the specifics of the particular background. These are the defined boilerplate prompt starters:



bprompt = f"""I need you to generate background art for a book. The style of the background I want generated is a sort of literary illustration style, which I've included an example of for helping guide the output image. The output should follow the style of that example — using its paper-like coloring — making sure to use period-accurate imagery/clothing/etc based on the provided setting and so forth. The background should not have any people or writing in it unless specified. The illustration should make strong use of hatching/cross-hatching in its style and shading, using clean lines.

The particular background """

A prompt doesn't necessarily need to use one of these for its third item, but note the important repeated emphasis on defining the image generation task in describing the relation to the book and the necessity for maintaining style and setting consistency. Whatever the base of the prompt, it needs to include those task-defining details.

Whereas the fourth item — the specific background details — is where the actual meat of the task lies. Getting this right involves balancing three requirements: having the background be consistent with the text, having the background be consistent with the other backgrounds (both stylistically and in terms of physicality), and having the background be good/pleasant/clean to look at. It's difficult to get backgrounds that satisfy all of these requirements on the first try, but that's why the automated script makes it easy to generate and re-generate attempts in batches for a human to review and curate into the best results. But such regenerating can still be time-consuming (and expensive), which is why getting the prompts as good as possible to begin with is still important. To that end, here's a bunch of heuristics for writing good prompts in this context:

- Prompts need to be detailed, incorporating both the explicit and implied details about a scene. Including short direct quotes from the book as part of prompting is good, and in general care should be spent to analyze all the ways a certain location is described throughout the book.
- Prompts need to not be *too* detailed. Current image generator technology is good, but not perfect, and the more details packed into a prompt, the less likely the image generator is to correctly include all the details. So some care needs to be taken in considering which details are most important to include, versus which can be safely dropped from the prompt itself. It's fine to skip over certain details/aspects of a scene as long as their absence doesn't create a text/visual contradiction. For example, if a text describes a room with all of its furniture, it's okay if every single bit of described furniture doesn't make it into the final background image, if the background ends up only showing one side of the room, since in that case the "missing" details can be assumed to just be behind the "camera". Taken to the extreme, fully abstract backgrounds that convey no information can also be acceptable, since again, if there are no details, there's no visual contradiction. Now, not every background should be fully abstract, but this idea of being selective about what to show, basing that partly off of what would be difficult to show correctly, is important.
- Prompts need to take into account the final hatching style, which will always be a tan-and-black line-drawing type illustration, reminiscent of the types of drawings found in physical books. One thing this means is that the book's descriptions of specific colors should often be dropped from the prompt. Later color palette normalization will collapse off-style colors anyway, though the normalization works less well the further off from the intended paper-coloring the base generated image starts as. In many cases, there's no need to specify colors at all, as the image generator will be able to safely assume them based on what's being described. In other cases, coloring does need to be specified, but it should generally be done so in terms of hatching density or shading: like for example light vs medium-light vs medium vs medium-dark vs dark/dense hatching. In particular for scenes at nighttime, that last one is how the sky should generally be described. Other aspects of the scene aside from color should also take into account the hatching effect in terms of best describing a good final look, such as for example often describing clouds or fog as "wispy". Overall then, it's just important to not have the prompts include instructions that visually contradict the intended style.
- Prompts should take into account the way the hatching style can be details in the foreground but gets progressively less detailed the further back into the image it goes. This is, in general, a good feature, because again it's best for backgrounds to not include overly detailed superfluous "information" that doesn't actually matter for the reading experience, and in fact just tends to distract from it. A big way this comes up is for people. In general, most backgrounds should not include people, because the main characters should always exist "above" the backgrounds as sprites, and even background characters tend to be distracting when they occupy the foreground of the background. That's why the primary `bprompt` boilerplate instruction includes the bit about not having people. However, in wider shots, especially in urban contexts, it can be more distracting to have no people at all, and so in those cases where it wouldn't make sense to avoid people, they should be included (switching to the `bpromptwithpeople` prompt), though ideally still tucked mostly into the background, with faces not too prominent. (Also for these cases: remember that with people come etiquette considerations, such as the necessity of needing the men to be wearing hats when outside in most public domain literary contexts, with such information often needing incorporating into the prompt.) Similar to people, text almost never looks good in the hatching style, and so the boilerplate prompts say to avoid including it unless specified, and it's rare that specifying text is actually desirable.
- Prompts should seek to display the most general version of a scene possible. By this, I mean that the details of a background might change over the course of a scene, such as a character picking up and moving an object, or lighting a fireplace, and so on. These "dynamic" aspects of the background require careful dancing around. We want to minimize the number of backgrounds, and so whenever there's a way to collapse two different versions of a background into one, it's generally a good idea to do so. For example, an object being moved doesn't require two separate backgrounds if that object is never shown in the background in the first place. Which again, may be okay, if the way background is presented implies it could be just off-screen. Or for example: if a backgrounds spans both day and night, two different versions of the background *can* be used (with the standard approach being to append the `-night` suffix to the background name), but perhaps the scene could also just have the curtains drawn throughout, preventing the outside from being seen, and avoiding the need to have multiple versions. These are just examples, and whether or not they can be taken advantage of depends highly on the specifics of the background. Some of the trickiest backgrounds to show, for example, are dining room scenes, where the contents of the table should technically continue to change over the course of the meal. Some cases like this require slight cheesing, where the main focus of the scene is put away from the dining table, which is given some generic dishes with some food, but not super zoomed in on in a way where the reader's focus is constantly put on how the dishes themselves aren't changing, or how the chairs are empty, with the characters only implied as sitting in them, when they really continue to exist only as sprites above the background. One way to help in this cheesing is to put such elements towards the bottom of the background, where they get partially obscured by the translucent text box. But again, case-by-case judgment is required here, which the parenthetical "vibe" intentions given for each background should help with.
- Prompts should seek to not overlap too heavily in contents with the prompts of the other backgrounds. The assigning of the needed backgrounds and the "vibe" hints should help with this, but still remember that the idea is that: the more overlap in the backgrounds, the more trouble it is to keep them consistent. So ideally, it's best to keep backgrounds to totally separate locations, utilizing tricks like blurred transitions (which the metadata-enhanced text has) to facilitate smooth transitioning from one to another. In some cases, physicality overlap is unavoidable, such as having shots of different ends of the same room, or shots of the interior and exterior of the same house — those cases will need to be ensured to be consistent through generated image curation. But smart prompting will also help greatly in reducing that work, via e.g., avoiding duplicating described features across multiple backgrounds. (Though even this is sometimes unavoidable when the same thing needs to be shown from multiple perspectives. In that case, prompting for consistency is key.)


Taking into account all of the above, you can see why some background prompts can end up taking many re-generations and even sometimes prompt retweakings to get right. And that's all fine, but since it'll be the human doing all that iterating and judging, they should be given as much help as possible in terms of making sure they're assessing the correctness of all the details correctly. As described above, prompts should not necessarily include every possible detail about a scene. However, it's helpful to include any extra supplementary details left out of the prompt itself as a python comment after the array line for the human to refer to for checking inconsistencies. For example, let's say you're setting up the prompt for a drawing room, and for whatever reasons, you determine that this particular shot would work best best if it doesn't include the bird mentioned as being off in one corner of the room. Include that information about the details left out in a comment like so:

    ["b-henry-music-night", brefs, bprompt, "should be of the luxurious music room of Lord Henry's estate, a place of aristocratic luxury and refined aestheticism, with oak-paneled walls and the view centered on the Victorian piano with a bench behind it, and other nice furnishings inside the small space (but no fireplace). It should be nighttime outside of the small leaded-paned silk-curtained window, represented by dense hatchings, with a couple Victorian gas light illuminating the room."], # Detail left out from 'across the room': 'a curious Java parrot, a large, grey-plumaged bird with pink crest and tail, that was balancing itself upon a bamboo perch'
    
These additional comment descriptions can use either direct quotes from the book or summarized descriptions as you determine best. (Such comments are good places to mention e.g., specific colors left out of the main prompts.)

And one other use of comments is this: in general, backgrounds tend to represent locations described in sufficient detail that the main challenge is in deciding which all details are most important to include in the prompt. However, in some other cases, backgrounds (or portions of them) may actually be *under*specified by the author. In some situations, that's fine, as the image generator can be assumed to fill in assumable detail as needed. However, in other cases, this has the effect of homogenizing certain parts of the output, such as for example if a "Victorian fireplace" is mentioned without any other detail, the same set of items always tends to appear in the generated image mantelpiece; or if for example a wall painting is specified, the same bit of landscape art always tends to be generated. In those kinds of cases, if authorial detail is lacking, custom detail can be added to the prompt, so long as the detail does not contradict anything said in the text. But in those cases, the fact that something is being *added* should be mentioned in the python comment after the array. (Also, both here and in the previous examples, don't overindex on the specifics, but just keep the general idea in mind, and then apply your best judgment to the text at hand.)
